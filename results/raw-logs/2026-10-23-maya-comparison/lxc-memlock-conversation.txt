Your configuration confirms this is an unprivileged Proxmox LXC container (CT 100) with 2 TiB of assigned memory and all four V620 GPUs passed through.

The existing configuration looks suitable for Maya. You do not need to change the GPU mappings, container privilege level, or memory allocation.

For the Engram locking requirement, add this line to CT 100's configuration:

lxc.prlimit.memlock: unlimited
On the Proxmox host, edit:

nano /etc/pve/lxc/100.conf

Add the line alongside your existing lxc.mount.entry setting. Keep the other settings unchanged.

LXC supports this setting directly, and the same fix has been confirmed for Proxmox containers with the default 8192 KiB memlock limit.

Next, configure Maya for full RAM residency. Since your HIP configuration is /opt/project-maya/maya-ds4-hip.json, run:

cd /opt/project-maya

python3 - <<'PY'
import json
from pathlib import Path

p = Path("maya-ds4-hip.json")
original = p.read_text()
cfg = json.loads(original)

assert isinstance(cfg["args"], list)
assert isinstance(cfg.get("env", {}), dict)

p.with_suffix(".json.bak").write_text(original)

cfg.setdefault("env", {}).update({
    "DS4_ENGRAM_RAM": "1",
    "DS4_REQUIRE_ALL_RAM": "1",
    "MAYA_DS4_Q8_BATCH": "1",
})

args = cfg["args"]
if "--mmap-experts" in args:
    args[args.index("--mmap-experts") + 1] = "off"
else:
    args.extend(["--mmap-experts", "off"])

p.write_text(json.dumps(cfg, indent=2) + "\n")
PY

Then benchmark with Maya's server stopped:

./maya.sh --backend hip --bench

The key things to verify in its output are Engram RAM ONLY, the number of CPU experts copied into RAM, and the actual generation throughput. The strict-residency options are designed to fail initialization rather than silently fall back to SSD.

For reference, we're comparing against Maya's previous 3.1 tok/s without DSpark and llamda's 11.56 tok/s.

If Maya remains slow despite complete RAM residency, our next investigation should focus on its DeepSeek HIP execution and multi-GPU scheduling rather than memory capacity.

Was this a problem for llama.cpp as well
Potentially, yes—but not necessarily in the same way.

Your previous llama.cpp benchmarks used:

-lm mlock -lzm off
-ot 'engram_embd=CPU;exps=CPU'

The important distinction is that -lm mlock requests memory locking; it does not raise the process's RLIMIT_MEMLOCK limit.

Before we fixed the container, that limit was only 8 MiB. If llama.cpp attempted to lock hundreds of gigabytes, those requests could not have succeeded under that limit.

That means our earlier assumption that the entire model was locked in RAM was not adequately verified.

However, failing to lock memory does not mean the model was necessarily being read from SSD. The Linux page cache can retain the GGUF files in RAM without mlock, particularly on your 2 TiB server.

I checked llama.cpp's implementation. When an mlock() call fails, llama.cpp logs a warning and continues rather than necessarily aborting.

There is another important detail: -lm mlock uses a non-mmap loading path, so your earlier benchmark may still have loaded the CPU weights into allocated system memory even though it could not lock them. In that case, the low memlock limit would not explain the poor throughput.

What I recommend
Before assuming anything about the effect, rerun your established llamda benchmark now that the memlock limit is fixed:

llamda-bench \
  -m /models/DeepSeek-V4.1-Flash-1017/UD-Q8_K_XL/DeepSeek-V4.1-Flash-1017-UD-Q8_K_XL-00001-of-00009.gguf \
  -ngl 99 \
  -ot 'engram_embd=CPU;exps=CPU' \
  --moe-cache-mib 65536 \
  -lm mlock -lzm off \
  -fa on \
  -t 32 \
  -b 8192 -ub 8192 \
  -p 8192 -n 1024 -r 2 \
  -o md

Your previous result was 132.11 tok/s prefill and 11.56 tok/s generation.

If those numbers improve substantially, the old memory-locking limitation may have mattered. If they remain similar, the bottleneck lies elsewhere.

I would also capture the startup log and look for failed to mlock warnings. That will tell us whether the old configuration was attempting and failing to lock memory.

Bottom line: The 8 MiB limit was a real configuration problem for any attempt to lock the model, but we have not established that it caused llama.cpp's poor performance.
